# ERC-8004 reputation, deduplicated by operator

[ERC-8004](https://eips.ethereum.org/EIPS/eip-8004) gives agents an identity registry, a reputation registry and a validation registry. The Identity and Reputation registries are deployed on Monad mainnet and testnet; the Validation registry is not deployed on Monad mainnet yet.

The spec is open about one weakness: feedback is only as good as its reviewers. `getSummary` takes a `clientAddresses` list because unfiltered results are open to Sybil and spam attacks, and the spec expects third-party systems to supply the filter. **Argus builds that filter from public chain data**: feedback clients first funded by the same non-hub funder are one operator.

## What it returns

```ts
import { createArgus } from '@argus/sdk';

const argus = createArgus({ network: 'mainnet', hypersyncToken: process.env.ENVIO_API_TOKEN });
const r = await argus.agentReputation(182);

r.raw.distinctClients        // 7665 wallets gave feedback
r.independent.operators      // 1 operator behind them
r.largestOperatorShare       // 1.0
r.clientAllowlist            // one client per operator: pass as clientAddresses to getSummary
```

Or from the command line: `npm run argus -w @argus/sdk -- reputation 182` (`--sample N` traces N clients for speed, `--json` for machines).

## Method

1. Read every `NewFeedback` and `FeedbackRevoked` event of the agent from the Reputation registry (HyperSync). Revoked entries are dropped.
2. For each feedback client, find its **first funder**: the sender of its earliest inbound native (MON) transfer of at least 0.01 MON. Feedback clients pay gas, so unlike x402 payers their funding is native.
3. Group clients by first funder. A group becomes **one operator** (Linked) when the same scoring rule as the rest of Argus holds:
   - **S1** the funder seeded at least 3 of the agent's clients and is not a known hub;
   - plus at least one of **S2** identical instalments (within 1%, 24 h), **S3** the clients first acted on the same UTC day, or **S5** the funder first funded at least 50% of the agent's clients (and at least 10 of them).
4. **S5 context concentration** is what lets the rule work for big funders. The generic hub rule never links a funder with more than 200 recipients, because exchanges and faucets look like that. But a funder that first funded most of *one agent's* reviewers is not behaving like an exchange. S5 never applies to a funder on the known-hub list.
5. Everyone else stands alone. Clients with no visible inbound MON transfer are counted as independent (benefit of the doubt) and reported as `unattributed`.
6. Means ignore feedback values beyond 1e15 (int128 extremes) and report how many there were.

Verdicts use public chain data only and say "shares a funder", never "fraud".

| #10182 | 78 | 16 | 9 | One fleet of 8 clients (identical 0.01 MON within 29 s, all active the same day); 7 clients have no visible MON funding |

The tags on agent #182's feedback (`eve`, `spawn`, `plague`) suggest a game or simulation, so a shared funder here is not evidence of bad intent. It still matters to anyone counting distinct reviewers: 7,665 wallets is one operator.

## Limits

- Funding is traced through **direct** native transfers. A wallet funded through a contract (a disperser, a faucet contract) shows no inbound transfer and is counted as unattributed.
- The known-hub list for native MON is empty by default; pass `knownHubs` for exchanges and faucets you want to protect from S5.
- With `--sample`, shares and counts describe the sample; the full run is exact but slower (about 3 minutes and 49 HyperSync queries for 7,665 clients on the free tier).
- ERC-8004 is a draft standard; the `NewFeedback` and `FeedbackRevoked` signatures were checked against the deployed contract.
